# Benchmark lab, phase 1 (2026-10-27)

First run of `tools/bench` (`@gamez/bench`), as planned in §7. It covers the ECS choice for the kernel, the kernel sim throughput, and the sync outbox and D1 apply batch sizes. The DO storage and workerd benchmarks are blocked (see below).

**Read these numbers as relative only.** They come from a shared local Node process on a Xeon, not from workerd, a real DO, or a browser.

## Machine

| Item          | Value                                     |
| ------------- | ----------------------------------------- |
| Node          | v24.22.1 (V8 13.6)                        |
| CPU           | Intel(R) Xeon(R) CPU E5-2660 v4 @ 2.00GHz |
| Logical cores | 46 (`/proc/cpuinfo`)                      |
| Memory        | 31.3 GiB                                  |

## Commands

Each benchmark is a package script in `tools/bench/package.json`. Run them from the repo root with `vp run`, using `--no-cache` so a cached result never stands in for a run:

```sh
node_modules/.bin/vp run --no-cache --filter @gamez/bench bench:machine   # CPU, node, memory
node_modules/.bin/vp run --no-cache --filter @gamez/bench bench:ecs       # ECS libraries (needs --expose-gc)
node_modules/.bin/vp run --no-cache --filter @gamez/bench bench:kernel    # kernel dispatch and step()
node_modules/.bin/vp run --no-cache --filter @gamez/bench bench:sync      # Outbox and applyBatch
node_modules/.bin/vp run --no-cache --filter @gamez/bench bench           # all of the above, in sequence
```

Each script writes JSON to `tools/bench/results/<name>.json`. The `bench:*` scripts run under `node --experimental-transform-types`, which prints an ExperimentalWarning on every run. That is expected.

Method: `tools/bench/src/lib.ts` warms up twice, then repeats each case for at least 1 s and at least 3 to 5 iterations (capped at 200), and reports the median. Units per second are computed from the median.

## 1. ECS: kernel World vs bitecs vs miniplex vs koota

### Heap retained per entity (50k, after GC)

| Case         |                  Bytes/entity |
| ------------ | ----------------------------: |
| kernel World |                           304 |
| bitecs, AoS  |                           351 |
| bitecs, SoA  |                           214 |
| miniplex 2   |                           205 |
| koota 0.6    | not valid (-17). See caveats. |

**Decision: ECS choice for the kernel.** Keep the kernel `World` for phase 1, and keep it behind the `World` interface in `packages/kernel/src/types.ts`.

- Iteration is the gap. The kernel pass runs about 20x slower than bitecs or miniplex (2.1M vs about 40M entities/s), and about 2x slower than koota (4.0M/s). Creation runs 3 to 10x slower than bitecs and miniplex.
- None of the libraries offers what the kernel needs. The kernel is deterministic and sorted, and it has JSON `snapshot()`/`restoreWorld()` and a state hash. bitecs SoA is fast only for numeric typed-array schemas, which would break the JSON component values the contracts require. Miniplex has no snapshot. Koota has no snapshot either.
- The per-dispatch cost matters more than ECS iteration here. See the kernel section: every dispatch snapshots the whole world. Fix that before any library swap.
- Revisit this at the scale phase, once there is a per-tick budget. If the pass gap becomes a real problem, measure bitecs SoA behind a snapshot adapter, not a rewrite.

## 2. Kernel sim

### Event-mode dispatch

Module: one action (`bench.bump`) that updates one counter, plus one system that runs after each resolved action. Dispatching goes through `sim.dispatch()`. Two worlds: one entity, and 1001 entities (1000 idle ones added).

| Case                                          | Median ms per batch | Dispatches/s |
| --------------------------------------------- | ------------------: | -----------: |
| event mode, world of 1 entity (batch 20k)     |                43.1 |      464,557 |
| event mode, world of 1001 entities (batch 2k) |               2,404 |          832 |

### Fixed-mode step()

Module: 1000 entities, each moved by one system, at 20 Hz. Measured as `step(100)` calls.

| Case                      | Median ms per 100 ticks | Ticks/s | Entity updates/s |
| ------------------------- | ----------------------: | ------: | ---------------: |
| fixed mode, 1000 entities |                    18.3 |   5,451 |        5,451,411 |

**Finding (not in the kernel bench's scope, but decision-relevant):** `Sim.dispatch()` calls `save()`, which runs `world.snapshot()` on every action so that a thrown error can roll back. The cost therefore scales with the world size. At 1001 entities a dispatch costs about 1.2 ms, against about 0.002 ms with one entity. That is a 560x drop in throughput for a 1000x larger world.

**Recommendation:** replace the whole-world snapshot in `dispatch()` with an undo log, or copy-on-write per component touched by the action. Keep the full snapshot for `snapshot()`, save and restore only. Track this as an ADR and a kernel task. It is out of scope for this benchmark, and the fix is in `packages/kernel`.

**Update:** done; see [`2026-10-kernel-rollback.md`](2026-10-kernel-rollback.md) for the undo log and its before/after numbers.

## 3. Sync: Outbox and applyBatch

Setup: `FakeSqlStorage` (DO side) and `FakeD1Database` (D1 side) from `packages/sync/tests/fakes.ts`, both backed by in-memory `node:sqlite`. Each cycle is 5,000 records over 500 keys. Commits are in-memory, so they are not durable and fsync costs are missing.

### Outbox: append in one transaction per batch, then `flush(maxBatch)`

| Batch | Median ms per cycle | Records/s | Sends per cycle |
| ----- | ------------------: | --------: | --------------: |
| 10    |                 676 |     7,392 |             500 |
| 100   |                 504 |     9,914 |              50 |
| 500   |                 511 |     9,782 |              10 |

### applyBatch into the D1 fake, replication batch size

| Batch | Median ms per cycle | Records/s |
| ----- | ------------------: | --------: |
| 10    |                 219 |    22,808 |
| 100   |                 185 |    26,970 |
| 500   |                 165 |    30,395 |

**Decision: outbox batch size.** Use **100** for both the flush `maxBatch` and the replication batch sent to D1.

- Outbox throughput is flat from 100 to 500 (about 10k records/s) and noticeably worse at 10. Each append does two SQL statements plus JSON, so the batch size barely moves it.
- applyBatch gains about 13% from 100 to 500 (27k to 30k records/s). That gain is capped by D1's 100-statement batch limit (`MAX_STATEMENTS_PER_D1_BATCH`): a 500-record batch is already split into six `db.batch()` calls. Staying at 100 keeps each D1 transaction short on the single writer and fits in one batch call.
- Batch 100 also keeps the number of queue messages down (50 per 5,000 records) without making each message large.

## 4. Not done in this phase

### DO storage (SQLite inserts inside a DO) — blocked

Attempt to run workerd-backed tests:

- `@cloudflare/vitest-pool-workers` 0.23.0 is **deprecated and renamed** (to `@cloudflare/vitest-plugin`). Its peer range is `vitest ^4.1.0`. Under Vitest 5.0.5 (bundled in Vite+), workerd starts, but the pool's proxy worker fails: `SyntaxError: Unexpected identifier 'file'`, and the pool reports "Failed to start cloudflare-pool worker".
- `@cloudflare/vitest-plugin` 1.4.9 (the successor, peer `vitest ^4.1.0 || ^5.0.0`) starts workerd. The suite then fails with `TypeError: Cannot read properties of undefined (reading 'config')`, in both the `vite-plus/test` and `vitest` import variants. The failure is inside the plugin harness.
- Both trial packages were removed again. Nothing in `tools/bench` depends on them.

Options for the next step (pick one):

1. Run the DO microbench through Miniflare 5 in a plain Node script (no Vitest).
2. Put the workerd tests in a separate package pinned to Vitest 4.1, outside Vite+.
3. Use `cf dev` with a small benchmark Worker and drive it over HTTP.

Option 1 is the cheapest and would also cover the DO fan-out benchmark. Miniflare 5 was only pulled in through the plugin trials, so it has to be installed again.

## Caveats

- **Relative numbers only.** This is a 46-thread shared Xeon running Node, not workerd, Durable Objects, D1 or a browser. Use the ratios and the trends, not the absolute numbers.
- **Small sample counts on slow rows.** The sync and kernel dispatch rows have 3 to 6 iterations. Batch-10 outbox (676 ms) vs batch-100 (504 ms) comes from only 3 samples each; treat the outbox ordering as indicative only.
- **ECS heap numbers are approximate.** They come from `process.memoryUsage().heapUsed` around one `populate` with `gc()` on both sides, and include object overhead, not just the components. The koota figure (-17 bytes) is not valid: koota destroys the previously populated world inside `populate`, so memory is released during the measurement. Treat koota's heap as unknown.
- **Koota create timing includes freeing the previous world.** Koota allows at most 16 live worlds per process, so `populate` destroys the old one. That cost is small compared with 50k spawns, but it is counted in the timing.
- **bitecs `addComponents` pitfall.** The first version used `addComponents(world, eid, Position, Velocity, Health)` with array components. Creation became quadratic (1k entities: 214 ms; 8k: 13.2 s) and the query returned zero matches. Calling `addComponent` once per component fixes both: linear, and the correct match count. Anyone using bitecs with array components should use the per-component calls.
- **Not like-for-like on updates.** The kernel's `read` + mutate is its documented system path (live stored values). The `update()` row is the safe, cloning path and is shown for completeness. The other libraries mutate in place, which is their idiomatic path.
- **Kernel dispatch numbers include the rollback snapshot.** That is the cost of the current kernel, not of the event model.
- **Sync numbers exclude real storage.** `node:sqlite` in-memory commits skip fsync, and the sink/queue is an in-memory array, so the real Queue send cost is not included.
- **Node flag warning.** `--experimental-transform-types` prints an ExperimentalWarning on each run. It is used because the kernel and sync sources use parameter properties, which Node's plain type stripping rejects.
