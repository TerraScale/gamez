# Shipping gamez: PWA, iOS and Android, desktop and Steam

Owner: wave C task T-ship (`docs/design/wave-C.md` §11). Decision record: ADR 0006 (to be
written by the integrator). This file is the runbook: what exists, how to test it, and what
is still open before a store submission.

| Target                                               | Status                                                                       | Where                                            |
| ---------------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------ |
| Installable PWA, offline shell                       | implemented, unit-tested, QA scenario `pwa`                                  | `apps/game/public/`, `apps/game/src/client/pwa/` |
| iOS and Android (Capacitor)                          | project files and docs; not built here (no Xcode or Android SDK in CI)       | `apps/native/capacitor/`                         |
| Desktop and Steam (Electron)                         | project files and docs; not built here                                       | `apps/native/electron/`                          |

Nothing in this file deploys, publishes or creates cloud resources. Store submissions are done by
hand, by the account owner.

## 1. PWA

### 1.1 What is in the build

| File                                       | Role                                                                                        |
| ------------------------------------------ | ------------------------------------------------------------------------------------------- |
| `apps/game/public/manifest.webmanifest`    | name, colours (`#10131a`, the app background), `display: standalone`, icons                 |
| `apps/game/public/icons/*.png`             | 192, 512, maskable 512, Apple touch 180, favicon 32. Generated by `tools/pwa/make-icons.ts` |
| `apps/game/public/sw.js`                   | the service worker (plain JS, not bundled, served as `/sw.js`)                              |
| `apps/game/index.html`                     | manifest link, theme colour, Apple meta tags, `viewport-fit=cover`                          |
| `apps/game/src/client/pwa/registration.ts` | the registration rules (pure, tested)                                                       |
| `apps/game/src/client/pwa/install.ts`      | the install prompt store (`installPrompt`) for the shell                                    |
| `apps/game/src/client/pwa/routing.ts`      | the routing table, mirrored by `sw.js` and checked by a test                                |
| `apps/game/src/client/main.ts`             | calls `registerPwa()` after the first render                                                |

Regenerate the icons after a design change (the output is deterministic):

```sh
node tools/pwa/make-icons.ts
```

### 1.2 When the worker registers

| Page                                           | Registers `/sw.js`? | Why                                                        |
| ---------------------------------------------- | ------------------- | ---------------------------------------------------------- |
| Production build on a real host (the Worker)   | yes                 | the normal case                                            |
| Production build on `localhost` or `127.0.0.1` | no                  | local previews should not hold a cache by accident         |
| Production build on localhost with `?sw=1`     | yes                 | for testing the offline behaviour locally                  |
| Vite dev server (`vp dev`, `:5173`, any host)  | **never**           | HMR and a cache do not mix; `?sw=1` does nothing there     |
| Any page with `?nosw=1`                        | no, and unregisters | removes the worker and the `gamez-*` caches for the origin |

`?nosw=1` wins over `?sw=1`. Use it once to clear a worker left behind by an earlier preview or a
production visit.

### 1.3 Caching strategy (`sw.js`, mirrored in `routing.ts`)

| Request                                           | Strategy                                                                                           |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| not `GET`, `/api/*`, `/ws*`, other origins        | not touched. The browser sends them as if there were no worker.                                    |
| page navigations                                  | network first, 3 s timeout, then the cached `/index.html`. The network answer refreshes the cache. |
| `/assets/*` (hashed by Vite) and `/art/*`         | cache first. Stored on the first successful answer. Error answers are not stored.                  |
| everything else (`/icons/*`, `manifest`, `sw.js`) | network (the browser's normal behaviour)                                                           |

Install precaches `/`, `/index.html`, the manifest and the icons, then crawls the `/assets/*`
graph: every file `index.html` refers to, every JS and CSS file those refer to, and so on (Vite's
chunks import chunks, and `__vite__mapDeps` lists the rest as bare `assets/…` paths). The crawl
found 33 files in the build of wave C; the install stores all of them. Two rules:

- a missing **asset** fails the install, so the app never installs half-cached (the browser
  retries later);
- a missing **icon** or other extra is skipped with a console warning.

Art (`/art/*`, 25 MB in the Kenney pack) is **not** precached. It is cache-first on first use, so
the first session that needs an atlas must be online. Precaching it would cost a mobile player
25 MB on install; a "download the art pack" option is the future path.

Offline with nothing cached: a small "gamez is offline" page (status 503), never the browser's
error page. Offline with the shell cached: the cached `/index.html` is served as a fresh
`Response` (see the note below) and the picker renders.

Two Chrome details that the QA run found and that the code now handles:

- A navigation fallback must be a **fresh** `Response` built from the cached text. Returning the
  cached `Response` (which keeps its URL, `/index.html`) fails the navigation to `/?sw=1` with
  `ERR_FAILED`.
- The build's responses carry `Vary: Origin`. A module script request sends an `Origin` header that
  the precached same-origin request did not have, so a lookup by request object misses offline.
  `/assets` lookups use the URL string, which has no headers, so they hit.

### 1.4 Cache versioning

- `CACHE = "gamez-shell-v1"` in `sw.js`, and `SHELL_CACHE` in `routing.ts` (the test checks that the
  two match).
- Bump the version (`gamez-shell-v2`) when the precache list, the routing or the strategy changes.
  Activate then deletes every other `gamez-*` cache.
- Hashed assets are never overwritten, so an open tab that loaded the previous build keeps working
  until it reloads. A new worker does **not** take over by itself: it waits until every tab is
  closed. The page may post `{ type: "SKIP_WAITING" }` to the waiting worker to take over at once,
  which is the hook for an "update available" toast (not built yet).
- Known growth: hashed assets from old builds stay in the cache until the version is bumped. A
  bump per release is the simple fix; pruning old asset hashes at activate is the next step if the
  cache grows too large. The art pack is cached on first use and is not pruned either.

### 1.5 How to test install and offline

Build the client and serve it on a port (the `pwa` QA scenario does this on 5410):

```sh
node_modules/.bin/vp -C apps/game build
node_modules/.bin/vp -C apps/game preview --port 5410
```

Open `http://localhost:5410/?sw=1` (localhost needs `?sw=1`; a real host does not).

1. **Manifest.** DevTools → Application → Manifest: name, icons (three entries) and "installable"
   shown with no errors.
2. **Worker.** DevTools → Application → Service workers: `sw.js` activated and running. Reload once
   so the page is controlled.
3. **Install.** Chrome or Edge: the install icon in the address bar, or the page menu → "Install
   gamez". Android Chrome: menu → "Install app". iOS Safari: Share → "Add to Home Screen" (the
   standalone meta tags make it open without browser chrome). Safari has no install prompt, so
   `installPrompt.getState().status` stays `unavailable` there.
4. **Offline, quick.** Load the page online once, reload, then DevTools → Network → Offline and
   reload. The shell renders. DevTools offline mode cuts the page's requests, but Chrome does not
   always cut the worker's own fetches, so this does not prove the cache served the reload.
5. **Offline, real.** Stop the server, then reload. Start a preview, let the page load and the worker
   take control, stop the preview process, and reload the page. The picker renders from the cache
   (the document comes back `200` with `fromServiceWorker: true`). This was run by hand for wave C
   (screenshot `waveC-ship-pwa/04-truly-offline.png`); it needs a running server to start with.
6. **Clear.** `?nosw=1` unregisters the worker and removes the caches. Reload without it to
   register again.

Chrome's "installable" check needs an icon of at least 192 px and a `start_url` the worker controls;
both are in place. The `pwa` QA run (section 1.7) records the installability errors that Chrome
reports over CDP (none on wave C's build).

### 1.6 Install prompt (for the shell)

```ts
import { installPrompt } from "./pwa/index.ts";

const state = installPrompt.getState(); // { status: "unavailable" | "available" | "installed", lastOutcome }
const off = installPrompt.subscribe((s) => renderInstallButton(s.status === "available"));
await installPrompt.prompt(); // "accepted" | "dismissed" | "unavailable"
```

`beforeinstallprompt` is captured and prevented from showing the mini-infobar. A prompt can be
shown once per event, and Chrome fires the event again later only after the user has engaged with
the site.

### 1.7 QA

`node tools/qa/src/run.ts pwa --out /tmp/gamez-qa/waveC-ship-pwa` against a running preview on
port 5410 (`GAMEZ_QA_PWA_URL` overrides the address). The scenario checks the manifest through
`Page.getAppManifest`, the installability errors through `Page.getInstallabilityErrors`, every icon
over HTTP, the worker's state and the precache, the offline reload (CDP emulation: see the limit in
section 1.5), and `?nosw=1`. It takes screenshots. The harness never starts the preview server:
start it first and stop it afterwards.

### 1.8 Tests

- `apps/game/tests/client/pwa.register.test.ts`: the registration rules and nosw cleanup, with
  fake service worker and cache objects.
- `apps/game/tests/client/pwa.install.test.ts`: the install store, with a fake window.
- `apps/game/tests/client/pwa.sw.test.ts`: evaluates `public/sw.js` in a `vm` sandbox with fake
  caches, fetch and timers. It checks that `sw.js` and `routing.ts` return the same route for a
  matrix of method, path and mode; the precache (including a crawled chunk graph, and failure of a
  missing asset); the reference parser (HTML attributes, `import()`, `url()`, `__vite__mapDeps`,
  and garbage in minified code); cache-first with an `Origin` header; the navigation fallback and
  timeout; and that API, WebSocket and cross-origin requests are never intercepted.
- `apps/game/tests/client/pwa.assets.test.ts`: the manifest fields, icon sizes read from the PNG
  headers, the `index.html` tags, and the `main.ts` call order.

Change `routing.ts` and `sw.js` together. The test fails when they drift.

### 1.9 Entry bundle budget

The entry graph is what `index.html` loads before the picker shows: the entry chunk plus its
static imports (not the `import()` chunks). Measured with gzip -9 on `vp -C apps/game build`:

| Build                   | Raw         | gzip      |
| ----------------------- | ----------- | --------- |
| Wave B (commit b9d157a) | 1,276,596 B | 390,606 B |
| Wave C before the fix   | 1,644,899 B | 507,070 B |
| Wave C as committed     | 1,321,208 B | 404,768 B |

What went wrong before the fix: the shell lazy-loaded its sheets with `import("@gamez/ui-host")`,
the same module the app imports statically, so the bundler kept every economy and play view in the
entry graph and, through the shared renderer module, the whole classic client chunk too. The views
now load from the `@gamez/ui-host/economy` and `@gamez/ui-host/play` subpaths, and the root index
re-exports only their types. `apps/game/tests/client/bundle-split.test.ts` guards both rules.

**Decision:** the remaining growth over wave B is accepted: +44.6 KB raw (+3.5 %), +14 KB gzip
(+3.6 %). It is the shell's economy bar, sheet stack and pollers, the wave C platform SDKs, and
classic content added in wave C. The economy, pass, store, arena and admin screens are their own
chunks (economy 46 KB, play, arena client 25 KB, admin 23 KB). The next large saving would be
loading `shared/catalog.ts` (the module code of every mode, about 350 KB of classic sim) only when
a mode starts. That needs light mode metadata for the picker, so it is left for a later wave.

## 2. iOS and Android (Capacitor)

`apps/native/capacitor/`: `capacitor.config.ts` (appId `dev.gamez.app`, `webDir` = the client
build output), `package.json`, `README.md` with the steps (install, `cap add`, `cap sync`, run,
live mode with `GAMEZ_LIVE_URL`, deep links, store notes).

Two modes, and the difference matters:

- **Bundled** works for the shell and single-player classic. The API calls go to
  `capacitor://localhost` and fail, so accounts, the bank, the market, shops and the arena need
  **live** mode.
- **Live** loads the hosted game in the webview. Use it for any store build that offers accounts.

Deep links return a sign-in (`#auth=`) or a payment (`#store=`, planned) to the app through
`appUrlOpen`. The glue is not in the repo yet (the README has a sketch).

Required before an iOS or Android submission (section 7): real Sign in with Apple, account
deletion inside the app, and no web checkout for digital goods inside the app.

## 3. Desktop and Steam (Electron)

`apps/native/electron/`: `main.mjs` (the window, external links in the browser, a single instance,
a minimal menu, permissions denied, optional Steam init behind `STEAM_APP_ID`), `preload.cjs`
(`window.gamezNative`, frozen, read-only), `package.json` with the electron-builder config, and a
`README.md` (dev run, packaging for Windows, macOS and Linux, code signing, Steam depot notes).

The window loads the hosted game. The desktop app contains no game code, so every launch shows the
current site. `PROD_URL` in `main.mjs` is a placeholder that stops the app until it is set.

`preload.cjs` is CommonJS on purpose: the sandboxed preload loader does not run ES modules. The
main process is ESM. Check both against the Electron version you install (the README says so).

## 4. Store submission checklists

### 4.1 Apple App Store (iOS)

- [ ] Apple Developer Program account; bundle id `dev.gamez.app`; App Store Connect app record.
- [ ] Sign in with Apple is real (not the stub), wherever Google or Discord sign-in is offered.
- [ ] In-app account deletion (guideline 5.1.1(v)) is implemented and tested. It is not in the repo
      yet, and this is a blocker when accounts exist in the app.
- [ ] Digital goods go through StoreKit (section 6). Web checkout is hidden in the app.
- [ ] Privacy policy URL, support URL, the App Privacy "nutrition label" (data types linked to the
      user, tracking: none unless added).
- [ ] Age rating questionnaire (the game includes fantasy combat; chat exists, so answer the
      user-generated-content and unrestricted-web-access questions honestly).
- [ ] Export compliance: the app uses HTTPS only. Set `ITSAppUsesNonExemptEncryption` in
      `Info.plist` after checking the current rules (unverified here).
- [ ] Screenshots for each required device size, the icon (1024 px, no alpha; generate it from
      the same design as `tools/pwa`), a review account for the reviewer.
- [ ] TestFlight build from live mode (section 2), tested on a device.

### 4.2 Google Play (Android)

- [ ] Play Console developer account; package name `dev.gamez.app`.
- [ ] Target API level meets the current Play requirement at the time of upload (check the
      console; not verified here).
- [ ] Data safety form matches section 5. Account deletion: a web link and an in-app path
      (Play requires both for apps with accounts).
- [ ] Content rating questionnaire (IARC). Ads: none.
- [ ] Digital goods through Play Billing (section 6).
- [ ] Store listing: short and full description (original text), screenshots, feature graphic,
      privacy policy URL.
- [ ] Internal testing track first, then closed, then production.

### 4.3 Steam

- [ ] Steamworks partner account, app id, depot ids (`apps/native/electron/README.md`, section 6).
- [ ] Store page: capsule art (original), trailer optional, system requirements, age rating
      (IARC or the Steam content survey), privacy policy.
- [ ] Steam Deck: test the window at 1280x800 and with controller input (the game is mouse and
      touch first; a controller pass is not done).
- [ ] Depot upload with SteamCMD, build set live on a branch after a private test.
- [ ] Steam microtransactions are **not** implemented (section 6). A launch without a store is the
      supported option for now.

## 5. Privacy and permissions

**Permissions.** The PWA asks for none. The Capacitor shell declares none (no camera, location,
contacts, photos or notifications). The Electron shell denies every permission request.

**Data the game stores.**

| Data                                                 | Where                                           | Why                        |
| ---------------------------------------------------- | ----------------------------------------------- | -------------------------- |
| session token                                        | `localStorage` in the browser (the web client)  | staying signed in          |
| classic save (single-player)                         | `localStorage` (the classic module's save slot) | playing without an account |
| account email, display name, sign-in provider id     | Worker D1 (read model) and AccountDO            | accounts, leaderboards     |
| character, bank, vault, trades, market, shops, arena | Durable Objects (authoritative), D1 read model  | gameplay and the economy   |
| purchase and order records (wave C §8)               | AccountDO, provider order ids                   | fulfilment (no card data)  |
| service worker caches                                | the browser cache (`gamez-*`)                   | offline shell              |

**Not collected by the client:** no analytics SDK, no advertising identifiers, no third-party
trackers. The economy telemetry (wave C §9) is server-side aggregate data.

**Open before a launch with accounts:** a privacy policy that names the data above; a way for a
player to request deletion (in-app on mobile, see section 4); a decision about players under 13 or
16 in the EU (age gating is not built); the payment providers' data processing terms (Stripe,
Asaas, Mercado Pago) for the web checkout.

## 6. Payments in stores (documented only)

Not implemented in wave C. The web payment providers (Stripe, Asaas, Mercado Pago, behind one
`PaymentProvider`, wave C §8) sell to web and desktop browsers only.

- **iOS and Android:** digital goods must use the platform billing: StoreKit and Google Play
  Billing. The planned route is **RevenueCat**, which wraps both stores and reports entitlements
  back to our Worker. The Worker side would verify RevenueCat's webhooks in the same way as the
  other providers. Nothing is built for it yet.
- **Steam:** microtransactions go through the Steamworks partner API (MicroTxn) with Steam's
  rules. Check Valve's current rules before selling in the Steam build through any other route.
  Not built.
- **Web checkout in app builds:** hide it in native builds (no link to purchase) until the
  billing above exists.

Costs to plan for (unverified, check the current published rates): platform fees on digital
goods, and the RevenueCat plan.
